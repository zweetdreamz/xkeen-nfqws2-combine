# Проверка маршрута, ресурсов и VPN/IP

Диагностический доступ подготавливается отдельной подтверждённой операцией. Схема трафика сохраняется:
Direct по умолчанию, VPN по правилам, одна вручную выбранная VPN-нода.

## Подготовка доступа

Нужны Python 3.12+, XKeen 2.1+ поколения 2.x, Xray 26.10.31+ поколения 26
и `curl` с HTTP2. Xray должен быть уже запущен.
В панели «Диагностика» нажмите «Подготовить доступ к диагностике» и подтвердите
перезапуск Xray. CLI-эквивалент из установленного проекта:

```sh
sh apply-discord-nfqws2.sh --setup-route-checker --yes-router
```

Движок проверяет полный конфиг, конфликты портов, policy marks и RCI, создаёт
rescue snapshot, публикует свои изменения и синхронно перезапускает Xray.
После рестарта проверяются живые API и обработчики; при ошибке восстанавливаются
исходные файлы и Xray. Выбор VPN-ноды, защищённый `04_outbounds.json`, nfqws2,
пользовательские правила DNS/SOCKS и завершающий Direct сохраняются.

Диагностика использует только loopback:

| Назначение | Адрес по умолчанию |
|---|---|
| Xray API: RoutingService и HandlerService | `127.0.0.1:10085` |
| SOCKS к активному `vless-reality` | `127.0.0.1:18445` |
| SOCKS к собственному plain Freedom | `127.0.0.1:18446` |

Совместимый существующий loopback API переиспользуется с сохранением его
services. Внешний адрес API, защищённая схема или конфликт порта приводят к
отказу. Собственный фрагмент — `99_kdn_inspection_tail.json`, его узкие правила
добавляются перед обычными правилами без изменения их порядка.

Файл `inspection-runtime.json` связывает конфиг с PID/starttime Xray после
проектного рестарта. Обычные проектные apply/rollback и переключение ноды
обновляют его после рестарта. Внешнее редактирование, ручной рестарт вне проекта
или перезагрузка устройства делают прежнее подтверждение недействительным:
чекер показывает непроверенный статус до явной повторной подготовки доступа.
Кнопка «Перезапустить» в блоке XKeen также меняет процесс и требует такой
подготовки; она сама не переиздаёт подтверждение диагностического доступа.
Если конфиг и подтверждённый процесс прежние, повторная подготовка не рестартует
службу. GET, проверки и монитор никогда не подготавливают доступ автоматически.

## Проверить маршрут

В «Диагностике» задайте домен и/или IP, inbound, TCP/UDP, порт назначения,
при необходимости IP и порт клиента. `TestRoute` спрашивает работающий Xray,
какой outbound он выберет для этого контекста. Сопоставление outbound с VPN
проверяется по живым настройкам обработчика, включая транспорт, а не по одному тегу.

Без IP используется до восьми ответов DNS роутера: для каждого показывается
отдельный результат. DNS клиента может отличаться. Без source IP/порта некоторые
правила не воспроизводятся; результат относится к введённому контексту.
Freedom/Direct может далее обрабатываться текущим nfqws2 и политиками Keenetic.
Решение Xray само по себе не доказывает доступность сайта, QUIC или звук Discord.
Конфиги с routing script/webhook не поддерживаются этим read-only чекером.

## Ресурсы Direct / VPN

Выберите ресурс из небольшого фиксированного списка, путь Direct/VPN или оба.
Обычная проверка получает HTTPS-ответ. Расширенная отдельно проверяет TLS1.2
и TLS1.3; TCP16 запрашивает ответ до 64 КиБ. Сертификаты проверяются, редиректы
не обходятся, произвольные URL и массовые IP-сканы не принимаются.

Путь проверяется на живом API до и после запроса. DNS-ответ закрепляется как
публичный IP назначения; curl передаёт его в SOCKS числом, сохраняя исходные
SNI, HTTP Host и проверку сертификата. Источник и порты соединения также
фиксируются и передаются в `TestRoute`. Неподтверждённый путь не запускает
сетевую пробу. VPN-проба не повторяется через Direct.

Показываются HTTP-код, объём чтения, задержка и причина незавершённой проверки.
Обрыв после 14–34 КиБ отмечается как наблюдение для сравнения путей. Таймаут,
reset, HTTP4xx и небольшой ответ сами по себе не доказывают DPI. Эти HTTPS/TCP
пробы не проверяют UDP/QUIC, голос или воспроизведение видео.

Методика TLS/HTTP и наблюдений TCP16 основана на
[Runnin4ik/dpi-detector](https://github.com/Runnin4ik/dpi-detector), MIT,
изучен commit `8d6d25a733f82e97a2aad8435072f8a1e3e43958`.
Его Python-зависимости, insecure SSL и массовые raw-IP/DNS проверки не переносятся.
Пробы, критерии успеха и расписание автоподбора стратегий остаются отдельными.

## Регулярный контроль активной ноды

В разделе «VPN-ноды» выберите контролируемые family: IPv4/IPv6 или обе.
Нажмите «Проверить текущую ноду». Проверяются живой outbound активного Xray,
выходной IP через HTTPS ipify и небольшой HTTPS canary. IPv4 и IPv6 используют
отдельные endpoints и адреса соответствующей family. Нода из резерва не подставляется.

Ожидаемые IP можно ввести вручную или явно одобрить свежее наблюдение (до 5 минут).
Одобрение привязано к конкретному результату, ID ноды и digest её подключения.
Новая нода или изменение подключения не наследуют старое одобрение. Если нода
сменилась во время редактирования, обновите форму перед сохранением.
Первый увиденный адрес никогда не принимается автоматически. IP сервера VPN
не считается доказательством выходного IP.

После одобрения IP проверьте поле «Контролируемые адреса», интервал и
переключатель включения, затем нажмите «Сохранить контроль и IP». Кнопка
«Одобрить наблюдаемый IP» сохраняет допустимые адреса; выбранные family и
периодичность сохраняются отдельно кнопкой настроек. Для IPv4-only должен
быть выбран вариант «Только IPv4», иначе потребуется одобрить и IPv6.
По умолчанию контроль выключен, интервал — 5 минут; допустимы 1..1440 минут.
Фоновый режим проверяет только VPN, не запускает Direct-сканы и не меняет ноду,
маршруты, firewall, стратегии, ожидаемые IP или службы. При занятости проекта,
восстановлении, неизвестной конфигурации или недоступном API проверка пропускается
либо остаётся непроверенной. Параллельные проверки не запускаются.

| Статус | Значение |
|---|---|
| IP совпадает, HTTPS доступен | Все выбранные family подтверждены, IP разрешены, canary доступен |
| IP изменился | Наблюдаемый IP отсутствует в явно одобренном списке |
| IP не одобрен | Для текущей конфигурации нет разрешённых IP |
| Неполная проверка | Часть family или их разрешённые IP не подтверждены |
| HTTPS не подтверждён | IP совпадает, canary не ответил успешно |
| Устарел / недоступен / пропущен | Положительного подтверждения текущего состояния нет |

История хранит до 100 изменений статуса/IP; повторяющийся результат не добавляет
новое событие. Config/state — отдельные файлы с правами 0600 в `/opt/etc/xkeen-web`.
Чтение статуса показывает кэш и не запускает пробу. Уведомления остаются в панели;
внешних ботов, сообщений или автоматического kill switch нет.

Монитор наблюдает IP, но не закрепляет NAT/IP у VPN-провайдера и не блокирует
трафик при несоответствии. Граница согласованности — проектный lock и собственные
процедуры рестарта. Произвольные параллельные изменения через root/Xray API
за пределами проекта не являются поддерживаемым способом управления конфигом;
внешние изменения требуют повторной явной подготовки.

## API и сохранённые результаты

| Запрос | Назначение |
|---|---|
| `GET /api/inspection/status` | Последнее ручное задание и его сохранённые результаты |
| `GET /api/vpn-monitor` | Настройки, одобренные IP, история и свежесть наблюдения рабочей ноды |
| `POST /api/inspection/check/route` | Проверка контекста TestRoute |
| `POST /api/inspection/check/resources` | Проверка Direct/VPN-ресурсов через API; отдельного блока в панели нет |
| `POST /api/inspection/check/vpn` | Ручная проверка активной ноды и IP |
| `POST /api/inspection/setup` | Явная подготовка доступа; отдельный job с возможным рестартом Xray |
| `POST /api/vpn-monitor/approve` | Одобрение конкретного свежего наблюдения |
| `POST /api/vpn-monitor/save` | Сохранение IP и настроек контроля для подтверждённой ноды |

POST защищены обычной same-origin охраной панели. Ручные проверки возвращают
202/job_id и опрашиваются через inspection status. Подготовка доступа использует
обычный route-job status/result. Одобрение и сохранение требуют актуальной
identity ноды; одобрение дополнительно связано с observation_id показанного IP.

GET не запускают сетевую проверку. Результаты маршрута/ресурсов относятся к дате
их выполнения; актуальность IP дополнительно сверяется с процессом и конфигом.
Время последней пробы видно в панели, история фиксирует только изменения.
Регулярный контроль выполняется процессом панели: закрытие вкладки его не
останавливает, а при остановленной панели новых проб нет. Это интервал, а не
расписание перебора стратегий по московскому времени.

## Уведомления

Во вкладке «Уведомления» можно включить/выключить отправку, выбрать события,
изменить тему ntfy и отправить тест. Сервер — ntfy.sh. Для варианта без
аккаунта токен не нужен. Тема создаётся случайной; знающий её имя может
читать/отправлять сообщения. В тексте нет IP, ключей, конфигов или raw errors.

Необязательный токен записывается приватно и не возвращается в браузер.
Это токен ntfy, не RCI-токен роутера.
Пустое поле сохраняет прежний токен; удаление — отдельный checkbox.
Смена темы требует подтверждения и очищает очередь старого канала.

События: проверенная ночная смена профиля, отсутствие кандидата, ошибка
ночного задания, подтверждённый откат, незавершённое восстановление,
изменение IP VPN, три неудачные проверки VPN подряд и восстановление.
Недоступный диагностический доступ — отдельное событие, не утверждение
о поломке VPN. Ноды/IP/маршруты автоматически не меняются.

Очередь — до32 сообщений, срок доставки24ч; повторы с задержкой до15мин.
При полной потере интернета немедленная доставка невозможна. Обычные повторы
дедуплицируются; авария между отправкой и записью подтверждения может дать
повторное уведомление. Статус последней доставки и очередь видны во вкладке.
Подписка на телефон/ПК настраивается в приложении или веб-интерфейсе ntfy.
