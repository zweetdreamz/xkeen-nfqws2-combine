# Локальная панель XKeen

`xkeen_control_script.sh` создаёт одностраничную панель:

- включить, выключить или перезапустить XKeen;
- для Discord TCP, Discord Voice, YouTube и Telegram независимо выбрать
  `Direct`, `Zapret` или `VPN` (у Telegram вместо `Zapret` — `WS`, и ещё `Выкл`);
- видеть этап и процент выполнения переключения;
- хранить историю переключений и вернуть состояние до выбранной операции;
- запускать проверки конфигурации и доступности после применения;
- подобрать актуальную стратегию YouTube, Discord TCP или Discord Voice прямо
  на роутере;
- проверить дату и commit последнего изменения Flowseal перед подбором;
- проверить и применить JSON-отчёт Windows-тюнера;
- выбирать сохранённые по дате версии профилей;
- вернуть встроенный профиль или откатить последнюю операцию импорта;
- увидеть текущий управляемый режим и результат команды.

## Значение режимов

На вкладке управления четыре карточки маршрутов (сетка 2×2):

| Карточка | Что переключает |
|---|---|
| Discord TCP | домены Discord: сайт, API, CDN, QUIC |
| Discord Voice | голос и STUN по UDP-портам |
| YouTube | сайт, видео, QUIC |
| Telegram | сайт, CDN, MTProto; `WS` — MTProto через WebSocket-ретранслятор на роутере, `Выкл` убирает правила проекта ([TELEGRAM.md](../../docs/TELEGRAM.md)) |

| Кнопка | Маршрут | nfqws2 |
|---|---|---|
| `Direct` | обычный WAN | выключен для сервиса |
| `Zapret` | обычный WAN | включён для сервиса |
| `VPN` | существующий VLESS outbound | выключен для сервиса |

При Discord Voice = `VPN` отдельного правила UDP-портов нет: голос идёт по
обычной proxy-маршрутизации XKeen.

Смена одного сервиса сохраняет режимы остальных. Backend вызывает
`set-service-route.sh`, поэтому получает snapshot, валидацию и автоматический
откат при ошибке. Переключение запускается отдельным фоновым заданием: панель
сразу принимает команду, затем опрашивает `/api/route/status`. Поэтому очистка
conntrack при перезапуске Xray не превращает корректную операцию в таймаут
браузера. Страницу можно закрыть и снова открыть — задание продолжится на
роутере, а панель подхватит его состояние. Пока идёт переключение, вкладки
остаются доступными; кнопки остановки подбора и теста после операции
возвращаются в состояние, соответствующее работающим заданиям.

Wrapper сохраняет и текущие настройки Discord UDP (`--wide-udp`,
`--udp-strategy`), поэтому импортированный широкий Voice-профиль не
сбрасывается при переключении другого сервиса.

## История, прогресс и проверка

Панель показывает этапы полного apply: preflight, snapshot, запись
конфигурации, перезапуск служб и финальную проверку. Проценты отражают этап,
а не точное оставшееся время.

Каждая операция маршрута записывается в
`/opt/etc/xkeen-web/history/<job-id>.json`. В записи остаются дата, режимы
четырёх маршрутов до и после, результат, хвост журнала и проверенный snapshot.
Кнопка **Вернуть состояние до операции** запускает обычный транзакционный
rollback выбранного snapshot. Перед ним создаётся rescue snapshot текущего состояния, поэтому
сам откат можно отменить следующей записью истории.

Если фоновое задание оборвалось (перезагрузка, нехватка памяти), операция
один раз помечается как прерванная, а snapshot из `Snapshot created:` в её
журнале сохраняется. Для такой операции тоже доступна кнопка **Вернуть
состояние до операции**: панель предупреждает, что роутер может быть в
промежуточном состоянии, а движок перед откатом создаёт rescue snapshot.

Проверка **Проверка после применения** выполняется после каждого успешного
изменения: смены маршрута, отката из истории, импорта, удаления и отката
профиля, применения версии и найденного автоподбором профиля. После ошибки
она не запускается. Backend возвращает результат проверки вместе с ответом,
поэтому её видят и прямые вызовы API. В проверку входят:

- процессы Xray и nfqws2;
- маршруты YouTube, Discord TCP, Discord Voice и Telegram по тем же правилам,
  что и `--status` (значки маршрутов): Discord TCP — правило `discord-direct`
  с доменами, Voice — отдельное UDP-правило `discord-direct` без доменов с
  портами Voice-профиля, YouTube — правило `youtube-direct`;
- файл routing, который реально использует Xray: последний `*.json` каталога
  конфигов с объектом `routing` (не обязательно `05_routing.json`);
- outbound проекта: `discord-direct`, `youtube-direct`, `telegram-direct`
  существуют, это `freedom` без `dialerProxy`/`proxySettings`, а `telegram-ws`
  перенаправляет на `127.0.0.1:18443`. Без outbound Xray молча отправляет
  трафик в первый outbound, обычно VPN;
- Telegram WS relay: PID из pid-файла принадлежит `telegram_ws_relay.py`, и
  `127.0.0.1:18443` принимает соединение;
- инварианты `nfqws2.conf` из `apply-discord-nfqws2.sh --check-config`
  (каждая строка `CHECK` — отдельный пункт). Если движок этой команды не
  знает, работает встроенная проверка: каждый порт `--filter-tcp/--filter-udp`
  профилей входит в `TCP_PORTS/UDP_PORTS`, а для YouTube=Zapret UDP 443 стоит
  в очереди и обрабатывается профилем с `youtube.list`;
- живые правила NFQUEUE: порты `nfqws_post/nfqws_pre` совпадают с
  `TCP_PORTS/UDP_PORTS` (иначе nfqws2 не перезапущен после изменения конфига),
  переходы из POSTROUTING/PREROUTING есть ровно по одному разу;
- для YouTube=Zapret — настоящий QUIC Initial к `www.youtube.com` через
  `tools/router/quic_probe.py`. Это проверка с самого роутера: она проходит
  через nfqws2 и провайдера, но не через Xray и не с телефона.

Предупреждения (например, порты в очереди без профиля) не делают проверку
проваленной и показываются отдельным списком. На вкладке управления остаются
краткий результат и кнопка **Открыть диагностику**. Подробные сетевые пробы
собраны там; Standard tests выполняет браузер по пути текущего LAN-устройства.

Backend сохраняет вывод apply во временный файл, а не в `subprocess.PIPE`.
Это существенно: запущенный Xray наследует stdout/stderr и может держать pipe
открытым уже после успешного выхода shell-скрипта, создавая ложный таймаут.
Реальный timeout завершает отдельную process group через `TERM`, чтобы shell
успел выполнить автоматический откат; затем используется `KILL` как аварийный
предел.

## Диагностика и Standard/DPI tests

Во вкладке **Диагностика** доступны три независимых запуска:

- **Проверить роутер** — всё из проверки после применения, а также `xkeen -xtest`,
  счётчики пакетов правил NFQUEUE (UDP и TCP, исходящие и ответы), default route
  IPv4, предупреждение, если IPv6 default route идёт через WAN при
  `IPV6_ENABLED=0` (такие соединения минуют nfqws2), DNS роутера в сравнении с
  DoH по закреплённым IP (Yandex `common.dot.dns.yandex.net@77.88.8.8`, Google
  `dns.google@8.8.8.8`, RFC 8484), различение блокировки по SNI и по IP через
  `curl --connect-to` с SNI `ya.ru` для Discord и YouTube (если они не через VPN),
  свободная память/диск, conntrack и другие обходчики DPI на роутере (nfqws,
  tpws, youtubeUnblock, b4, byedpi/ciadpi, DPITunnel, SpoofDPI и второй nfqws2).
- **Standard tests** — HTTPS GET из браузера по 15 HTTPS-целям: основные цели
  Flowseal плюс Discord API, YouTube `generate_204`, Googlevideo `report_mapping`.
  Ping-цели исключены: браузер не умеет ICMP или принудительный выбор TLS.

- **DPI 16–20 КБ** — 12 узлов разных провайдеров из hyperion-cs/dpi-checkers.
  Браузер делает HTTPS GET и POST со случайными 64 КиБ на каждый узел
  (до 768 КиБ отправки), параллельно работают не более трёх задач.
  Таймаут и ошибка отмечаются как неопределённые: CORS скрывает код ответа
  и фактически переданный объём. Проверка не доказывает DPI-блокировку.

Блок **Проверить в приложении** сохраняет ручные шаги Discord Voice/UDP и
YouTube QUIC/HTTP3 из прежней проверки после применения. Проверка роутера
также сверяет каждый service-direct маршрут с наличием/отсутствием nfqws2-профиля:
`Discord TCP route`, `Discord Voice route`, YouTube и, если он управляется,
`Telegram route` проверяются отдельно.

Это адаптация [Flowseal service.bat](https://github.com/Flowseal/zapret-discord-youtube/blob/main/service.bat)
и [test zapret.ps1](https://github.com/Flowseal/zapret-discord-youtube/blob/main/utils/test%20zapret.ps1).
Проверки используют текущий профиль и не вызывают start/stop/restart служб.
Списки целей включены в нашу версию панели с SHA источников; проверка GitHub
во вкладке подбора не обновляет эти списки автоматически.

Standard/DPI tests выполняются только из браузера и используют маршруты
данного устройства: например, YouTube → Zapret, Discord TCP → VPN. Собственный
VPN/прокси на компьютере меняет путь. Результат «ответ получен» может означать
HTTP 403/404. Ошибки также возможны из-за перенаправления, расширения или
политики браузера. Для точного теста UDP используйте Discord-приложение.

Браузерные тесты требуют открытой страницы; результаты живут до её обновления.
При открытии панели старые серверные Standard/DPI-отчёты не отображаются.
Сохраняется только результат проверки роутера с явной подписью и датой.
**Остановить тест** прерывает активные запросы и очередь. Проверка роутера
по-прежнему работает фоновым заданием в `/opt/tmp/xkeen-diagnostics`.
Запуск Standard/DPI через backend и CLI отключён. Подбор стратегий сохраняет
собственные проверки — это отдельный механизм.

Кнопка **Скачать Windows-helper** загружает `reset-discord-cache.ps1`.
Запустите его на компьютере из PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\reset-discord-cache.ps1
```

Helper запрашивает подтверждение, закрывает Discord и переименовывает только
`Cache`, `Code Cache`, `GPUCache`, сохраняя резервные папки с датой. Он не
меняет сетевые настройки Windows. Проверки Windows-служб/WinDivert из
Flowseal на Keenetic не переносились.

## Автоподбор на роутере

Ручной подбор использует автономные пробы с роутера, отдельно от браузерных
Standard/DPI tests. Перед остановкой штатного nfqws2 записывается исходный
результат (`baseline`); он служит сравнением и не пропускает запрошенный вручную
поиск. Для временного кандидата нужно два успешных прохода подряд:

Во временном процессе сохраняется полный набор остальных рабочих профилей и
исходные TCP/UDP-порты. Voice-перебор заменяет только `NFQWS_ARGS_UDP`, сохраняя
Discord TCP/QUIC и YouTube. TCP-перебор заменяет только `NFQWS_ARGS`; YouTube —
только custom-секции с `youtube.list`. Остальные custom-секции сохраняются.
Аргументы собираются штатной функцией `_startup_args` init-скрипта; если она
недоступна, подбор завершается до остановки службы. Короткая пауза при смене
самого процесса nfqws2 остаётся возможной.

- YouTube: HEAD сайта, JSON oEmbed с `title`, загрузка тестовой миниатюры.
  HEAD `redirector.googlevideo.com` — дополнительный транспортный индикатор;
  он не доказывает загрузку видео. Миниатюра и oEmbed используют фиксированный
  публичный ролик `jNQXAC9IVRw`; сбой этой цели отражается и в baseline.
- Discord TCP: HEAD приложения, ответ API `/api/v10/gateway` с адресом gateway,
  загрузка стандартной картинки CDN. Один HTTP 200 без ожидаемого содержимого
  не считается достаточным. WebSocket-сессия пока не проверяется.
- Discord Voice: сохраняется reconnect и подтверждение звука пользователем.
  Диагностика дополнительно отдаёт численные наблюдения исходящих/входящих UDP
  и совпадения endpoints на WAN. Эти счётчики не подтверждают звук автоматически.
  Автоподбор умеет отсеивать кандидатов по трафику самого Discord — см.
  [проверку по трафику](#проверка-discord-voice-по-трафику).

Каждая проба фиксирует этап, номер прохода, код curl/HTTP, время, размер и
причину отказа. В JSON-отчёте есть `verification` с baseline, пробами и границами
проверки: QUIC, реальное воспроизведение видео и автоматическая оценка голоса
пока не подтверждаются. Пробы IPv4/TCP обходят proxy-переменные curl; на данном
роутере nfqws2 перехватывает исходящий трафик в POSTROUTING. Это не тест
прозрачного пути LAN → Xray. На других установках нужно отдельно проверить hook.

Повторный проход увеличивает время поиска. Ошибка восстановления nfqws2
завершает задание ошибкой, даже если проходной кандидат ранее был найден.
Расписание, автоматический запуск при поломке и автоприменение пока отсутствуют.

1. Сначала переведите подбираемый сервис в `Zapret`: подбор проверяет маршрут
   именно Discord TCP, Discord Voice или YouTube. Telegram автоподбор не
   поддерживает: провайдер блокирует его по IP, и стратегии Zapret не помогают.
2. Откройте вкладку **Автоподбор** и выберите сервис.
3. Для первого запуска оставьте `Safe` и 32 кандидата, а в поле
   **BAT-файл Flowseal** — все файлы.
4. Нажмите **Начать подбор**.
5. Для Discord Voice выберите **Проверка Voice**: «По трафику Discord» — один
   раз зайдите в голосовой канал и оставайтесь в нём; «Вручную» —
   переподключайтесь под каждого кандидата и отвечайте **Да** или **Нет**.
7. Если найден победитель, отдельно нажмите **Применить найденный профиль**.

YouTube и Discord TCP проверяются HTTP-пробами автоматически. Это первичный
фильтр: после применения всё равно проверьте воспроизведение ролика или
приложение. Discord Voice нельзя надёжно оценить HTTP-запросом, поэтому он
остаётся полуавтоматическим: даже автоматическая проверка заканчивается
подтверждением звука.

Для Discord TCP панель рассчитывает на доменный `discord-direct`. Категория
`ext:zkeenip.dat:discord` не должна присутствовать в Xray: из-за общих сетей
Cloudflare/Google она может затронуть ChatGPT и другие сервисы.

Во время задания:

- актуальные `general*.bat` загружаются из Flowseal и только разбираются как
  данные;
- постоянные конфиги Xray/XKeen/nfqws2 не записываются;
- временно останавливается штатный процесс `nfqws2`, проверяется кандидат и
  через `EXIT` trap восстанавливается исходная служба;
- Xkeen не вызывается;
- панель блокирует смену маршрутов, управление Xkeen и постоянные операции с
  профилями.

Кнопка **Остановить и восстановить nfqws2** отменяет фоновое задание. При
закрытии браузера оно продолжает работать; состояние снова появится после
открытия вкладки. После потери питания временный процесс исчезает, а при
обычной загрузке стартует сохранённая постоянная конфигурация `nfqws2`.

Поля seed в панели нет: роутер создаёт новое 32-битное число при каждом
запуске. Основной allowlist-пул перемешивается отдельно от отложенных
кандидатов с rank 200+. При небольшом лимите меняется не только порядок, но и
подмножество. Seed записывается в состояние задания и в результирующий отчёт;
повторить тот же порядок можно из командной строки
(`zapret_autotune_job.py --search-seed`).

Результат не применяется автоматически. Отдельная кнопка применения проходит
ту же строгую проверку, что и импорт Windows-отчёта, создаёт focused snapshot
и перезапускает только `nfqws2`.

В блоке **Обновления Flowseal** одна кнопка **Проверить обновление**.
Если commit ветки `main` совпадает со скачанным набором, панель пишет
**Актуально**. Иначе скачивает все `general*.bat` по одному закреплённому
commit и пишет **Новые стратегии скачаны**. Рабочие профили не заменяются.

Набор хранится в `/opt/etc/xkeen-web/flowseal-sources.json`: до 64 файлов,
не более 256 КиБ каждый и 4 МиБ в сумме. Запись атомарная; при ошибке загрузки
предыдущий набор сохраняется. BAT разбираются как данные и не исполняются.
Ручной подбор из панели использует эту скачанную копию; при её отсутствии
скачивает стратегии с GitHub как прежде. Для обновления уже сохранённого
набора сначала нажмите кнопку проверки. Commit рабочего профиля может быть
старее набора — это не ошибка и не повод автоматически его заменять.
Windows-тюнер по-прежнему самостоятельно загружает актуальные стратегии.

### Проверка Discord Voice по трафику

Режим **Проверка Voice → По трафику Discord** (по умолчанию,
`zapret_autotune_job.py --voice-traffic`) не требует переподключаться под
каждого кандидата. Перед стартом зайдите в голосовой канал и оставайтесь в
нём. Пока голос не подключён, Discord сам переподключается, и каждая попытка
идёт через текущего кандидата. Роутер следит за трафиком компьютера
(`diagnose-discord-voice.sh`, окно 25 с) и выдаёт
`EVENT|VOICE_TRAFFIC|состояние`:

| Состояние | Что значит |
|---|---|
| `connected` | новый поток начался с запроса IP Discovery (74 байта), и сервер отвечает не меньше 8 с — голос держится |
| `attempts` | Discord пытается подключиться, но поток не держится |
| `established` | голос был подключён ещё до окна; о кандидате это ничего не говорит |
| `idle` | голосового трафика нет — компьютер не в канале |

Кандидат без `connected` отбрасывается без вопросов; для найденного профиля
панель один раз просит подтвердить звук. Перед кандидатами то же окно
проверяет текущий профиль: `idle` — зайдите в канал, `connected` или
`established` — голос уже работает, подбор не нужен. Признаки взяты из
реального журнала: у рабочего соединения клиент и сервер обмениваются
пакетами примерно раз в секунду даже в тишине.

### Проверка Discord Voice пакетом с роутера

Режим **Проверка Voice → Пакетом с роутера** виден для Discord Voice и включается,
когда сохранён голосовой сервер. Задание запускается с
`zapret_autotune_job.py --voice-auto`. Сервер показывает
`GET /api/tuner/voice-endpoint`.

Откуда берётся сервер:

1. Пройдите обычную ручную Voice-проверку. Во время окна reconnect
   `scripts/diagnose-discord-voice.sh` выбирает самый активный публичный
   endpoint на портах, которые обрабатывает каждый Voice-кандидат
   (`19294-19344`, `50000-50100`), который
   ответил клиенту, и печатает
   `EVENT|VOICE_ENDPOINT|IP|PORT|OUT_PACKETS|IN_PACKETS`.
2. Ответ **Да** завершает подбор найденным профилем, и задание сохраняет этот
   сервер в `/opt/etc/xkeen-web/discord-voice-endpoint.json` (IPv4 и порт,
   время в `learned_utc`). Неподтверждённый результат сервер не обновляет.
   Runner запускает диагностику через `sh`, бит исполнения не нужен.

Как работает проба. `tools/router/discord_voice_probe.py` (только
стандартная библиотека Python) отправляет с роутера на сохранённый сервер три
запроса Discord IP Discovery по 74 байта — так клиент начинает голосовую
сессию. Профиль Voice в nfqws2 выбирает именно этот payload
(`--payload=stun,discord_ip_discovery`), поэтому запрос проходит через
проверяемую стратегию. Ответ засчитывается, только если он имеет тип ответа
IP Discovery и повторяет SSRC запроса. Результат:
`EVENT|VOICE_PROBE|LABEL|SENT|RECEIVED|VALID`.

Ход подбора:

1. Калибровка: проба с текущим активным профилем, затем при полностью
   остановленном nfqws2 (без его правил firewall).
2. Если сервер отвечает и без обхода, проба ничего не различает: панель
   пишет «Автопроверка выключена…», и каждый кандидат проверяется вручную,
   как без флажка.
3. Иначе кандидат без корректного ответа отбрасывается автоматически, без
   reconnect. Кандидат с ответом открывает обычное окно Voice: переподключитесь
   и подтвердите звук. **Нет** — перебор продолжается.
4. Если в автоматическом режиме на вопрос о звуке никто не ответил за
   `TUNER_VERDICT_TIMEOUT` секунд (по умолчанию 300), профиль остаётся
   найденным, но помечается «Звук не подтверждён». Перед применением
   проверьте голос вручную. При ручной проверке молчание по-прежнему
   означает **Нет**.

Ограничение: на реальном роутере ещё не проверено, отвечают ли голосовые
серверы Discord на IP Discovery вне активной сессии. Если не отвечают ни с
одной стратегией, автопроверка отбросит всех кандидатов. Если при этом не
ответил и текущий профиль, панель пишет, что адрес мог устареть; тогда
снимите флажок. Windows-тюнер оставляет только ручную проверку.

### Один BAT-файл Flowseal

Поле **BAT-файл Flowseal** позволяет быстро проверить готовый конфиг одного
файла. Список берётся из скачанного набора (`GET /api/tuner/sources`) и
появляется после **Проверить обновление**. Файлы без профиля для выбранного
сервиса недоступны для выбора.

С выбранным файлом проверяются только его профили: без встроенного профиля
роутера и без смешивания с другими BAT. Сначала, всегда первыми, идут
переведённые профили файла. `Safe`/`Extended` затем добавляют тот же перебор,
что без выбора файла применяется к встроенному профилю, но от профиля этого
файла: для Discord Voice — `repeats` и `out-range`, для TCP и YouTube —
`out-range`, `repeats`, `pos`, `tcp_seq`, `seqovl` и сочетания (меняются только
параметры, которые есть в профиле; у `hostfakesplit` их меньше). Например,
`general (ALT9).bat` для Discord Voice даёт 1, 6 или 12 кандидатов. Имя файла видно в статусе
и записывается в отчёт как `source_file`. Фоновое задание получает его как
`zapret_autotune_job.py --source-file`.

### Сколько кандидатов и из каких файлов

Одинаковые после перевода профили проверяются один раз: повторять ту же
стратегию нет смысла. Поэтому кандидатов бывает меньше, чем BAT-файлов. В
Flowseal `176f56d` у Discord Voice 19 из 22 файлов дают один и тот же профиль
(`fake:blob=discord_udp:repeats=6`), ALT12, ALT13 и EXP отличаются только
`repeats`; с встроенным профилем получается 5 кандидатов. Для каждого
кандидата журнал пишет строку вида

```text
Кандидат 2 из 5: general (ALT).bat (тот же профиль ещё в 18 файл(ах): general (ALT10).bat, …) · fake-udp
```

а встроенный профиль подписан как «встроенный профиль проекта».

## Импорт профиля тюнера

На вкладке **Импорт профиля** выберите один из файлов:

```text
tools\windows\reports\youtube-latest.json
tools\windows\reports\discord-tcp-latest.json
tools\windows\reports\discord-voice-latest.json
```

Отчёт должен содержать найденного кандидата, а соответствующий сервис уже
должен работать в режиме `Zapret`. Панель дважды проверяет схему, ID кандидата,
allowlist опций, hostlist и границы портов: сначала в Python backend, затем в
router shell. Верхняя граница портов Discord Voice берётся из строки
`# Discord UDP: strategy=…, range=…` в `nfqws2.conf`, как в движке: 50100 для
`narrow`, 65535 только для `wide`.

При применении:

1. создаётся отдельный снимок `/opt/etc/nfqws2`;
2. профиль сохраняется в `/opt/etc/nfqws2/imported-profiles`;
3. точная копия получает UTC-дату в
   `/opt/etc/nfqws2/profile-versions/<service>`;
4. заново генерируется управляемый блок;
5. перезапускается и проверяется только `nfqws2`.

Xkeen/Xray не изменяется, не останавливается и не перезапускается. При ошибке
восстанавливается только снимок `nfqws2`. Кнопка отката возвращает состояние
до последнего импорта или удаления профиля. Старые версии можно выбрать по
дате и применить отдельно; это тоже проходит проверку, создаёт focused
snapshot и требует перезапуска только `nfqws2`.

## Установка

Скопируйте проект на роутер, затем:

```sh
cd /opt/root/keenetic-discord-nfqws2
sh tools/router/xkeen_control_script.sh
```

Установщик создаёт только:

```text
/opt/xkeen-web/app.py
```

Он не запускает сервер, не меняет маршруты и не добавляет автозапуск.

На текущем роутере используется уже существующий init-script
`/opt/etc/init.d/S99xkeen-web`; после установки приложение запущено через
него.

Ручной запуск:

```sh
/opt/bin/python3 /opt/xkeen-web/app.py
```

Открыть:

```text
http://192.168.2.1:8088
```

По умолчанию сервер привязан только к LAN-адресу `192.168.2.1`, а не ко всем
интерфейсам.

## Настройка путей

Перед запуском можно задать:

```sh
XKEEN_WEB_BIND=192.168.2.1
XKEEN_WEB_PORT=8088
XKEEN_PROJECT_DIR=/opt/root/keenetic-discord-nfqws2
```

Пример:

```sh
XKEEN_WEB_PORT=8090 /opt/bin/python3 /opt/xkeen-web/app.py
```

## Безопасность

- команды заданы фиксированным allowlist и не собираются через shell;
- JSON ограничен 512 КиБ, а nfqws2-аргументы проходят строгий allowlist;
- route POST требует специальный same-origin header;
- POST принимает только настроенный числовой LAN Host, что также ограничивает
  DNS rebinding;
- запросы от непубличных LAN/loopback адресов разрешены, остальные
  отклоняются;
- Flowseal BAT разбираются allowlist-парсером и никогда не исполняются;
- фоновое задание использует общий project lock и запрещает конфликтующие
  изменения;
- переключение маршрута имеет собственный job ID и журнал в
  `/opt/tmp/xkeen-route-switch`; параллельный apply через панель блокируется;
- переключение, подбор и проверка роутера стартуют под одной блокировкой:
  второй запуск, пока первый ещё стартует, сразу получает HTTP 409
  («другое задание уже запускается»);
- постоянная история хранит только проверенные snapshot из управляемого
  каталога; произвольный путь передать в rollback нельзя;
- GitHub-проверка имеет таймаут 30 секунд и не исполняет полученные данные;
- пароли в панели не хранятся.

Панель не имеет входа по паролю. Любой клиент, который уже имеет доступ к
этому LAN-адресу и порту, может переключать маршруты. Не пробрасывайте порт
`8088` в интернет и не публикуйте его через reverse proxy без отдельной
аутентификации.

## Перед использованием

На роутере должны находиться:

```text
apply-discord-nfqws2.sh
set-service-route.sh
tools/router/zapret_autotune_job.py
tools/router/discord_voice_probe.py
tools/router/xkeen_diagnostics.py
scripts/diagnose-discord-voice.sh
tools/windows/reset-discord-cache.ps1
tools/windows/zapret_tuner.py
tools/windows/router-candidate-runner.sh
```

Переключение маршрута выполняет обычный транзакционный `apply`, поэтому может
на несколько секунд перезапустить Xray и nfqws2. Панель ждёт его до 15 минут
в фоне и показывает фактический вывод apply или автоматического отката.
Импорт профиля — отдельная
операция: она перезапускает только nfqws2. Сам подбор также временно
перезапускает только nfqws2; запуск выполняется лишь после нажатия кнопки.

Во вкладке **Автоподбор** доступны три глубины: прямой перевод BAT, `Safe`
с изменением одного параметра и `Extended` с ограниченными сочетаниями.
Панель принимает от 1 до 64 кандидатов, по умолчанию 32. В перебор входят
`repeats`, `out-range` и TCP `pos`/`seq` (QUIC-часть YouTube не подбирается); полный декартов
перебор намеренно не используется. Порядок каждый раз новый (seed создаёт
роутер).

## Откат версии панели

При управляемой установке старая панель и backend сохраняются в
`/opt/etc/xkeen-web-backups`, после чего доступны одной командой:

```sh
sh /opt/root/keenetic-discord-nfqws2/tools/router/rollback-xkeen-web.sh
```

Этот launcher возвращает версию приложения и backend-скриптов. Он не меняет
выбранные маршруты сервисов; для них используется обычный
`rollback-last-change.sh`.
